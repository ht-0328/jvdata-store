# jvstore — JRA-VAN Data Lab. のデータを DuckDB に貯める

JV-Data仕様書に載っている**蓄積系32表を DuckDB に貯める**ツールです。
過去N年ぶんを指定できますが、収録開始と提供期間は種別ごとに異なります。

**取得だけを担います。** レースや馬を選んで絞り込む機能は持ちません。
絞り込みと分析は、このデータベースを読む側（[`keiba-yosou`](https://github.com/ht-0328/keiba-yosou)）の責務です。

> [!TIP]
> **JV-Data の仕様そのものは [ドキュメントサイト](https://ht-0328.github.io/jvdata-store/) にまとめてあります**
>
> レコードの読み方・データ種別・コード表・全38レコードの項目表です。
> このツールの使い方（ここ）とは分けてあります。ソースは [docs/](docs/index.md) にあります。
>
> - [JV-Data の全体像](docs/01-overview.md) — 何が配信され、どう受け取るか
> - [レコードの読み方](docs/02-record-format.md) — 固定長レコードの解き方
> - [データ種別と提供タイミング](docs/03-dataspecs.md) — 何をいつ取れるか
> - [レコードのつながり](docs/04-relations.md) — 38表の結合
> - [レコード索引](docs/reference/index.md) / [コード表](docs/reference/codes.md)

## 画面で取得する

**このフォルダの [`run.bat`](run.bat) をダブルクリック**してください。
**操作パネル**（小さなウィンドウ）が開き、サーバーが止まっていれば起動して、ブラウザで取得・管理画面を開きます。
`jvdata-store` だけで動きます。`keiba-yosou` のインストールや起動は不要です。

```powershell
# 保存先とポートを変える
run.bat --db D:\keiba\jvdata.duckdb --port 9000

# 操作パネルを使わず、コンソールで動かす（Ctrl+C で終了）
uv run python -m jvstore.cli serve --open
# → http://127.0.0.1:8766/
```

### 起動・停止・画面の開き直し

サーバーの起動・停止・画面の開き直しは、操作パネルで行います。
ブラウザからはサーバーを起動できないため、ブラウザの画面とは分けています。
同じ説明は、ブラウザの画面右上の「使い方」でも見られます。

| やりたいこと | 操作 |
| :--- | :--- |
| 起動する | `run.bat` をダブルクリック。止まっていれば自動で起動し、画面が開く。停止後は操作パネルの「起動」 |
| 閉じた画面を開き直す | 操作パネルの「画面を開く」。操作パネルも閉じていたら `run.bat` をもう一度ダブルクリック |
| 停止する | 操作パネルの「停止」。取得の途中なら「終わってから停止しますか？」と聞かれる。「はい」で取得が終わったときに自動で停止、「いいえ」で停止しない |
| 停止の予約をやめる | 操作パネルの「予約を取り消す」 |

- ブラウザのタブや操作パネルを閉じても、サーバーは止まりません。
- **取得の途中で止めることはできません。** 途中で止めると、データが途中までしか入らないためです。
- 操作パネルから起動したサーバーの出力は、`%TEMP%\jvstore-serve-<ポート>.log` に書かれます。起動できなかったときは、その末尾を操作パネルに表示します。

1. 利用キーが未登録なら「JV-Link設定」で登録します（設定画面はこのPCに開きます）。
2. 年数（1〜40年）とデータ種別を選び、「取得する」を押します。
3. 取得後は表を選んで件数・期間・中身を確認できます。開催日による絞り込みは閲覧だけに効きます。

通常は初回に指定年数のうち提供されている範囲を取り、2回目以降は差分を更新します。
**1年から10年などに期間を広げる場合は「期間を広げて再取得する」にチェック**してください。
取得ログ・成功・失敗を表示し、ブラウザの再読み込み後も実行中の処理へ再接続します。

保存先は画面に表示します。既定はこのフォルダの `jvdata.duckdb` です。
画面は `127.0.0.1` のみで待ち受け、よそのサイトから送られた操作（取得・停止）は受け付けません。

データの取得はこの画面だけで行います。`keiba-yosou` の予想画面には取得の入口を置いていません。
`keiba-yosou` の予想画面と同時に開いても、両方の画面が `<DBパス>.ui.lock` を使うので、
取得と閲覧・予想が同時にDBを開くことはありません。
CLIや他のアプリから同じDBを扱う場合は、取得の終了を待ってください。

## コマンドで取得する

```powershell
uv sync

# 過去10年ぶんの蓄積系データをまとめて取る
uv run jvstore sync --years 10 --db jvdata.duckdb

# 件数だけ先に確認する
uv run jvstore sync --years 10 --dry-run

# 種別を絞る
uv run jvstore sync --years 3 --dataspec RACE,DIFN
```

種別ごとに、**初回はセットアップ取得（option=4）、2回目以降は前回の続き（option=1）**です。
仕組みと注意点は「[2回目以降は「続きから」取ります](#2回目以降は続きから取ります)」を読んでください。

初回は数十分〜数時間かかり、保存先が数GBになります。

## 取得する範囲

| データ種別ID | 内容 | 収録される表 |
| --- | --- | --- |
| `RACE` | レース情報 | RA SE HR H1 H6 O1〜O6 WF JG |
| `DIFN` | 蓄積情報 | UM KS CH BR BN RC RA SE |
| `BLDN` | 血統情報 | HN SK BT |
| `SNPN` | 出走時点情報 | CK |
| `MING` | マイニング予想 | DM TM |
| `SLOP` / `WOOD` | 調教 | HC / WC |
| `YSCH` | 開催スケジュール | YS |
| `HOSN` | 競走馬市場取引価格 | HS |
| `HOYU` | 馬名の意味由来 | HY |
| `COMM` | 各種解説（コース情報） | CS |
| `TOKU` | 特別登録馬 | TK |

この12種別で**蓄積系の32表を取得対象にします**。全表を同じ期間に揃えられるとは限りません。

**`TOKU`（特別登録馬）は、セットアップでは今週・来週分のみです。** 過去分は
`fetch --dataspec TOKU --option 1` に開始時刻を指定して別途取得します
（[JV-Linkインターフェース仕様書 4.9.0.1 p.21 注1](https://jra-van.jp/dlb/sdv/sdk/JV-Link4901.pdf#page=21)）。
ハンデ発表後の通常データの提供期間は1年間なので、2026年9月時点で2023年分を
新たに取得することはできません
（[JV-Data仕様書「データ提供タイミング･提供単位」](https://jra-van.jp/dlb/sdv/sdk/JV-Data4901.pdf#page=54)）。
`--force-setup` でも、この制限は変わりません。

> [!IMPORTANT]
> **旧種別は使いません**
>
> `DIFF` / `BLOD` / `SNAP` / `HOSE` ではなく `DIFN` / `BLDN` / `SNPN` / `HOSN` を使います。
> 新種別は繁殖登録番号・生産者コード・生産者名のサイズ拡張に対応しており、
> 同梱のレイアウト定義（JV-Data仕様書 4.9.0.1 準拠）と一致するのは新しい方です。
> **旧種別を取ると `UM` と `BR` のバイト位置がずれ、エラーにならずに壊れた値が入ります。**

速報系専用の表（`WH` 馬体重・`WE` 天候馬場・`AV` 取消・`JC` 騎手変更・`TC` 発走時刻・
`CC` コース変更）は、サーバの提供期間が1週間なので「過去N年」の対象にできません。
発走前のオッズ・人気も、蓄積系には確定したあとのものしか入りません。
これらは開催日を指定して `jvstore realtime`（画面なら「速報の取得」）で取ります。

## 「過去10年」が指す範囲

`JVOpen` の読み出し開始時刻は**提供された時刻**であって、開催日ではありません
（JV-Linkインターフェース仕様書 p.17）。本ツールは指定された年数から
**その年の1月1日**を求めて渡します。JV-Link はセットアップデータを月単位の
ファイルで持っているため、月の途中を指定しても意味がないからです。

```
2026年に --years 10 を指定 → 20160101000000 以降に提供されたデータ
```

JRA-VAN の提供開始は 1986 年なので、それより前には遡りません。

**ただし、1986年まで揃うのはレース詳細・馬毎レース情報・払戻・票数だけです。**
3連単オッズは 2004年8月以降、3連複は 2002年6月以降しかありません。
レコードごとの収録開始時期は
[データ種別と提供タイミング](docs/03-dataspecs.md#セットアップで遡れる範囲) にあります。

また、**通常データはサーバに1年しか置かれません**（JV-Data仕様書「データ提供
タイミング･提供単位」の提供期間）。1年より前に遡れるのはセットアップデータだけなので、
初回は必ずセットアップを通します。

## 2回目以降は「続きから」取ります

**`sync` は同じ範囲を2回取りません。** 前回どこまで取ったかを覚えていて、
次からはその続きだけを取ります。

### どうやって覚えているか

`JVOpen` は、対象になったファイルのうち**最も新しいファイルの時刻**を返します
（`lastfiletimestamp`。JV-Linkインターフェース仕様書 p.19 が、次回の `fromtime` に
使うため保存しておくよう求めています）。

これをデータ種別ごとに、データベースの `_meta` 表へ1行ずつ書いておきます。

| key | value |
| --- | --- |
| `sync:RACE` | `20260906120000` |
| `sync:DIFN` | `20260906120000` |

次に `sync` を実行すると、この行があるかどうかで動きが変わります。

| `_meta` の行 | 読み出し開始時刻 | option | 取れるもの |
| --- | --- | --- | --- |
| ない | `--years` から求めた1月1日 | 4（セットアップ） | 収録開始以降の過去N年ぶん（TOKUは今週・来週分のみ） |
| ある | 保存してある時刻 | 1（通常データ） | 前回以降の差分だけ |

**記録するのは、そのデータ種別を読み切ったあとです。** 途中で失敗すれば記録されないので、
次回また同じ範囲を取り直します。中途半端な位置から再開して、穴が空くことを防ぐためです。

進捗を別ファイルに持たないのは、**データと進捗がずれないようにするため**です。
データベースを消せば進捗も消え、コピーすれば進捗ごとコピーされます。

### 期間を広げるときは `--force-setup` が要ります

> [!CAUTION]
> **1年取ったあとに10年を取っても、9年ぶんは入りません**
>
> `--years` を大きくしても、`_meta` に行があるかぎり動きは「続きから」のままです。
> **エラーは出ず、短時間で正常終了します。** 古い年が入っていないことに気づけません。
>
> ```powershell
> uv run jvstore sync --years 1                  # 1年ぶん取る
> uv run jvstore sync --years 10                 # 差分だけ。9年ぶんは入らない
> uv run jvstore sync --years 10 --force-setup   # これが正しい
> ```

`--force-setup` は `_meta` を無視して、セットアップ取得をやり直します。
**同じデータを2回入れても行は重複しません**
（[なぜ重複しないか](#同じデータを2回取り込んでも行が増えない理由)）。
余分にかかるのは時間だけです。

### 古い年だけを足すときは `tools/fetch_past_years.py`

`--force-setup` は、指定した年から**今日までを全部読み直します**。すでに入っている
新しい年まで読み直すので、そのぶん時間がかかります。
足りない年だけを読むなら、終わりの月を指定できるこのスクリプトを使います。

```powershell
# 2016年1月〜2022年12月を取り込む（レース情報から順に、坂路調教が最後）
uv run python tools/fetch_past_years.py --from 201601 --to 202212

# 対象ファイル数だけ確かめる（DB は変えない）
uv run python tools/fetch_past_years.py --from 201601 --to 202212 --dry-run
```

- 期間は**月の単位**で指定します。`--to 202212` なら2022年12月分まで入ります。
- `_meta` は動かしません。次の `sync` は、これまでどおり前回の続きから取ります。
- 取り込み中は画面と同じロックを取るので、画面を開いていると始まりません。
- `DIFN` `HOSN` `HOYU` `COMM` `TOKU` は終わりの月を指定できないので、対象にしません。
  `TOKU` 以外は全件が提供されるので、`sync` で一度取っていれば古い年の分も入っています。

> [!WARNING]
> **`jvstore fetch --to` に日付の終わり（`20221231235959`）を渡すと、12月分が入りません**
>
> セットアップのファイルは月ごとで、JV-Link はファイル名の `年月99`＋提供時刻
> （例: `2022129920230808…`）と、指定した時刻を文字として比べます。
> `20221299…` は `20221231…` より大きいので、12月のファイルが対象から外れます。
> このスクリプトは、終わりを「最後の月の翌月1日0時」（`20230101000000`）で渡します。

> [!TIP]
> **一度に開くファイルを少なくすると、読み出しが速くなります**
>
> JV-Link は、一度に開くファイルが多いほど、1レコードの読み出しが遅くなります
> （[JV-Linkインターフェース仕様書 4.9.0.1 p.17](https://jra-van.jp/dlb/sdv/sdk/JV-Link4901.pdf#page=17)「既知の障害」）。
> 実測では、140ファイルなら1回0.08ミリ秒、1,260ファイルなら約2ミリ秒でした。
> このスクリプトは1年ずつ（レース情報なら約180ファイル）に区切って開きます。

### 進捗を確かめる・消す

```powershell
uv run python -c "import duckdb; print(duckdb.connect('jvdata.duckdb', read_only=True).execute('SELECT * FROM _meta').fetchall())"
```

まだ1度も取り込んでいなければ `[]` が返ります。

行を消せば、そのデータ種別は次回セットアップからやり直します。
データベースごと消しても同じです。

## データベースの形

**1つの表が1つのテーブル**になります。テーブル名はレコード種別IDの小文字（`ra`, `se`, …）、
列名は仕様書の項目名そのままです。

**繰返しブロックは子テーブルに分けます。** 仕様書の表をそのまま横に並べると
`H6 票数6（3連単）` が 14,720 列になり、扱えなくなるためです。

```
h6                 開催年 … レース番号 ＋ 発売票数など            (34列)
h6__3連単票数       同じキー ＋ _連番 ＋ 組番/票数/人気順          (10列)
```

| 表 | 仕様書のまま | 親テーブル |
| --- | ---: | ---: |
| `H6` 票数6（3連単） | 14,720列 | 34列 |
| `O6` オッズ6（3連単） | 14,702列 | 15列 |
| `TK` 特別登録馬 | 3,036列 | 37列 |
| `O5` オッズ5（3連複） | 2,462列 | 15列 |

値は**仕様書の桁のままの文字列**です。`競馬場コード='01'`、`単勝オッズ='0054'`（＝5.4倍）
のように、先頭のゼロもコード値も落としません。数値化やコード変換は読む側で行います。

主キーは仕様書の「キー」列です。ただし**オッズ表（O1〜O6）には `発表月日時分` を足して**
います。仕様書のキーはレースキーだけなので、そのままだと時系列オッズの断面が
1つしか残りません。

書き込みは冪等です。同じレコードを2回入れても行は増えず、`データ作成年月日` と
`データ区分` で**新しい版だけが残ります**。削除レコード（データ区分=0）は行を消さずに
残すので、古いファイルを読み直しても削除が取り消されません。

**この仕組みを実データで追った説明が
[同じデータを2回取り込んでも行が増えない理由](#同じデータを2回取り込んでも行が増えない理由)
にあります。**

## 同じデータを2回取り込んでも行が増えない理由

**結論から言うと、ファイル名は一切見ていません。** レコードの中身から主キーを切り出し、
DuckDB の `PRIMARY KEY` に当てています。以下、実際に流したデータで順に追います。

再現に使ったコマンドはこれです。読み取り専用の `fetch` なので、`jvdata.duckdb` は触りません。

```powershell
uv run jvstore fetch --dataspec RACE --from 20260825000000 --to 20260901000000 `
    --option 1 --db demo.duckdb --only RA
```

### 手順1 — JV-Link が返してくるファイル名

上のコマンドで `JVGets` が返したファイル名は、25個ありました。抜粋します。

```
JGDW2026082920260828112817.jvd
RASW2026082920260831133220.jvd
RASW2026083020260831133221.jvd
SESW2026082920260831133222.jvd
O1SW2026082920260831133212.jvd
```

`RASW2026082920260831133220.jvd` は次のように分かれています。

| 部分 | 値 | 意味 |
| :--- | :--- | :--- |
| 1〜2文字 | `RA` | レコード種別ID（レース詳細） |
| 3〜4文字 | `SW` | 配信区分。観測できたのは `SW`（週明けの確定）と `DW`（前日） |
| 5〜12文字 | `20260829` | 対象の開催日 |
| 13〜26文字 | `20260831133220` | 配信された時刻 |

> [!WARNING]
> **ファイル名では重複を判定できません**
>
> 理由は2つあります。
>
> 1. **1ファイルに複数のレースが入っています。** `RASW2026082920260831133220.jvd`
>    には8月29日の36レースが全部入っており、行の識別には粗すぎます。
> 2. **同じレースが別名のファイルで何度も届きます。** 上の期間の `RA` は確定後の
>    `SW` だけですが、期間を9月5日以降に広げると `RADW2026090520260904112825.jvd`
>    が現れます。同じレースが前日（`DW`）と週明け（`SW`）の両方で配信されます。
>    裏付けは手順4のデータ区分です。
>
> なお **JV-Linkインターフェース仕様書はファイル名の書式を定義していません**
> （p.27 の `JVGets` の `filename` は「現在読み込み中のファイル名」とだけあります）。
> 上の分解は実データの観察であって、仕様に保証されたものではありません。
> **だから、ファイル名に依存した実装にしていません。** ログに出すだけです。

### 手順2 — レコードの中身を切り出す

`JVGets` は1回の呼び出しで**固定長の1レコード**を返します。実際に返ってきた
RA レコードの先頭28バイトがこれです。

```
RA72026083120260829010203011
```

JV-Data仕様書「２．レース詳細」（レコード長 1272 バイト）の項番1〜9と突き合わせます。

| 項番 | 項目名 | 位置 | バイト | 実際の値 | キー |
| ---: | :--- | ---: | ---: | :--- | :---: |
| 1 | レコード種別ID | 1 | 2 | `RA` | |
| 2 | データ区分 | 3 | 1 | `7` | |
| 3 | データ作成年月日 | 4 | 8 | `20260831` | |
| 4 | 開催年 | 12 | 4 | `2026` | ○ |
| 5 | 開催月日 | 16 | 4 | `0829` | ○ |
| 6 | 競馬場コード | 20 | 2 | `01` | ○ |
| 7 | 開催回[第N回] | 22 | 2 | `02` | ○ |
| 8 | 開催日目[N日目] | 24 | 2 | `03` | ○ |
| 9 | レース番号 | 26 | 2 | `01` | ○ |

「キー」列の ○ は**仕様書がキーとして指定している項目**です。手で選んだものではなく、
`JV-Data仕様書_4.9.0.1.xlsx` のキー列をそのまま読み取っています
（`src/jvstore/resources/layouts.json` に生成済み。`uv run jvstore spec columns RA` で見られます）。

### 手順3 — どのテーブルに入れるか

**先頭2バイトがそのままテーブル名になります。** `RA` なら `ra` です
（`record_id_of()` が先頭2バイトを読み、対応する `TableSpec` を引きます）。

作られるテーブルの定義は次のとおりです。実際に `demo.duckdb` から取り出したものです。

```sql
CREATE TABLE ra(
  "レコード種別ID" VARCHAR, "データ区分" VARCHAR, "データ作成年月日" VARCHAR,
  "開催年" VARCHAR, "開催月日" VARCHAR, "競馬場コード" VARCHAR,
  "開催回[第N回]" VARCHAR, "開催日目[N日目]" VARCHAR, "レース番号" VARCHAR,
  ... （全99列 ＝ 仕様書の98項目 ＋ 後述の `_版`） ...,
  PRIMARY KEY("開催年", "開催月日", "競馬場コード", "開催回[第N回]", "開催日目[N日目]", "レース番号")
);
```

**`PRIMARY KEY` の6列が、手順2の表で ○ が付いていた項目と一致しています。**
この6つが揃えば1つのレースが一意に決まるので、同じレースの行は2行になりません。
なろうとすれば DuckDB が制約違反で落とします。

主キーは表ごとに違います。`_tables` テーブルに全表ぶん記録してあります。

| 表 | 主キー |
| :--- | :--- |
| `ra` レース詳細 | 開催年, 開催月日, 競馬場コード, 開催回, 開催日目, レース番号 |
| `se` 馬毎レース情報 | 上記6列 ＋ 馬番, 血統登録番号 |
| `um` 競走馬マスタ | 血統登録番号 |
| `o1` オッズ1（単複枠） | 上記6列 ＋ **発表月日時分** |

> [!NOTE]
> **オッズ表だけ主キーを足しています**
>
> 仕様書の `O1`〜`O6` のキーはレースキーだけです。そのままだと時系列オッズ
> （`0B41`/`0B42`）を貯めたときに、**同じレースの断面が1つしか残りません**。
> `発表月日時分` を主キーに足して、5分刻みの断面を別の行として残しています
> （`_EXTRA_KEYS`）。仕様書から外れる唯一の箇所です。

> [!NOTE]
> **子テーブル（`h6__3連単票数` など）には主キーを付けていません**
>
> 3連単の票数・オッズの子テーブルは、10年分で1億行を超えます。主キーがあると、
> 1行入れるたびに索引で重複を確かめるので、書き込みが遅くなり、索引のぶんメモリも使います。
> 3連単が7千万行ある DB で、6万レコードの書き込みが274秒から215秒になりました。
>
> 子テーブルの重複は、親が置き換わったときに子を丸ごと消してから入れ直すことで
> 防いでいます（`store.py` の `_merge_child()`）。
> 以前の版で作った DB は、その表に初めて書き込むときに主キーを外して作り直します。
> 3連単が7千万行ある DB では、全部の子テーブルで3分ほどかかります。

### 手順4 — 同じレースは何度も配信される

JV-Data仕様書「２．レース詳細」項番2「データ区分」には、こう書かれています。

```
1:出走馬名表(木曜)  2:出馬表(金･土曜)  3:速報成績(3着まで確定)
4:速報成績(5着まで確定)  5:速報成績(全馬着順確定)
6:速報成績(全馬着順+コーナ通過順)  7:成績(月曜)
A:地方競馬  B:海外国際レース
9:レース中止  0:該当レコード削除(提供ミスなどの理由による)
```

**1つのレースについて、木曜から月曜までに最大9回、主キーが同じレコードが届きます。**
上書きしないと古い情報が残り、素朴に追記すると同じレースが9行に増えます。

### 手順5 — どちらを残すかを決める `_版`

そこで、全テーブルに `_版` という列を1つ足しています。中身はこれだけです。

```
_版 = データ作成年月日 ＋ データ区分
```

データ区分は3つだけ読み替えます。文字列として比較したときに、
**残したいものが必ず大きくなる**ようにするためです。

| データ区分 | `_版` での文字 | 意図 |
| :--- | :--- | :--- |
| `0` 該当レコード削除 | `Z` | 最強。削除は何にも上書きされない |
| `9` レース中止 | `Y` | 次に強い |
| `A` 地方競馬 / `B` 海外国際 | `8` | 中央の `1`〜`7` より後ろ |
| `1`〜`7` | そのまま | 数字が大きいほど確定に近い |

実データでは `データ作成年月日=20260831`、`データ区分=7` だったので、
`_版` は **`202608317`** になりました。

反映のときは、主キーが同じ行のうち `_版` が大きいものだけを残します。

以下は主キーの結合条件を `主キー` と略した形です。実際は6列の `AND` 結合になります
（`store.py` の `_merge()`）。

```sql
-- 既存より新しいものだけを勝ち残らせる
CREATE OR REPLACE TEMP TABLE tmp_won AS SELECT s.* FROM tmp_latest s
WHERE NOT EXISTS (SELECT 1 FROM ra t WHERE t.主キー = s.主キー AND t."_版" > s."_版");

DELETE FROM ra t USING tmp_won s WHERE t.主キー = s.主キー;
INSERT INTO ra SELECT * FROM tmp_won;
```

`>` であって `>=` ではないので、**同じ版を取り直したときは既存を置き換えます**
（値は同じなので結果は変わりません）。古い版を読み直しても `NOT EXISTS` が偽になり、
`tmp_won` に残らないので**巻き戻りません**。

### 手順6 — 実際に2回流した結果

```
1回目: 合計 2,729 レコード / 0.4 秒 → RA レース詳細 72 件
       ra 行数: 72

2回目: 合計 2,729 レコード / 0.4 秒 → RA レース詳細 72 件
       ra 行数: 72
```

**2,729レコードを読み直しても、行は72のままです。** 72 は、この期間の
8月29日・30日の全レース数です。

1行目の中身も確かめられます。

```
('2026', '0829', '01', '02', '03', '01', '7', '20260831', '202608317')
 開催年  開催月日 競馬場 開催回 日目  R番号  区分  作成年月日   _版
```

手順2で切り出したバイト列と、1文字ずつ一致しています。

## 発走前・当日のデータを取る（速報系）

**何が問題か。** 「取得する」（`jvstore sync`）で入るのは、確定したあとのデータだけです。
発走前のオッズ・人気・馬体重・天候と馬場状態・マイニング予想・取消や騎手変更は、速報系でしか取れません。

**何をすればよいか。** 開催日を指定して、その日の速報をまとめて取ります。画面なら「速報の取得」で
開催日を選んで「速報を取得する」、コマンドなら次のとおりです。1日ぶんで1分もかかりません。

当日の分は、このフォルダの [`realtime_today.bat`](realtime_today.bat) をダブルクリックしても取れます
（`realtime_today.bat --date 2026-09-27` のように、後ろに付けた引数は `jvstore realtime` に渡ります）。

```powershell
uv run jvstore realtime --date 2026-09-20                      # 明日のぶん（前日の夜に）
uv run jvstore realtime --date 2026-09-20 --date 2026-09-21    # 何日ぶんでも
uv run jvstore realtime                                        # 省略すると今日
```

取るものは次の6つです（`src/jvstore/realtime.py`）。まだ発表されていないものは「該当データなし」と出て、
失敗にはなりません。何度取り直しても構いません。同じ鍵の行は新しい版に置き換わり、オッズだけは
発表時刻（`発表月日時分`）ごとに行が残ります。

| データ種別 | 中身 | 入る表 | いつから取れるか |
| :--- | :--- | :--- | :--- |
| `0B15` | 速報レース情報（出馬表・取消・騎手変更の反映。当日は成績と払戻） | `ra` `se` `hr` | 木曜の出走馬名表から |
| `0B14` | 速報開催情報（天候・馬場状態、取消、騎手変更、発走時刻変更、コース変更） | `we` `av` `jc` `tc` `cc` | 前日から |
| `0B11` | 速報馬体重 | `wh` | 発走の約1時間前 |
| `0B13` | タイム型マイニング予想（前日予想 → 当日予想 → 直前予想） | `dm` | 出馬表の発表後 |
| `0B17` | 対戦型マイニング予想（同上） | `tm` | 出馬表の発表後 |
| `0B30` | 速報オッズ（全賭式。単勝・複勝・枠連・馬連・ワイド・馬単・3連複・3連単） | `o1`〜`o6` | 発売が始まってから（前日発売があれば前日の夜から） |

オッズは**レース毎にしか取れません**。開催日単位で取る方法は仕様上ないので、その日のレースの数だけ呼びます
（レースの一覧は、先に取った `0B15` の `ra` から拾います）。速報の提供期間は1週間です。

1種別・1レースだけを取りたいときは `jvstore rt` を使います。

```powershell
# 開催日単位（出馬表〜成績）
uv run jvstore rt --dataspec 0B15 --key 20260905 --db jvdata.duckdb

# レース単位（オッズ・全賭式）。--only で表を絞れる（例: 3連単を外す）
uv run jvstore rt --dataspec 0B30 --key 2026090506040109 --only O1,O2,O5 --db jvdata.duckdb
```

時系列オッズ（`0B41` 単複枠・`0B42` 馬連）は**提供期間が1年**あり、過去のレースでも
レースキーを指定すれば5分刻みの断面が取れます。3連複・3連単の時系列はありません。

## CSV でほしいとき

`--out` を付けると DuckDB ではなく CSV に書き出します。1表1ファイル、
ヘッダは仕様書の項目名（繰返しは連番付きで平坦化）です。

```powershell
uv run jvstore fetch --dataspec RACE --from 20260801000000 --only RA,SE --out out
```

## つまずきやすいところ

- **`--years` を増やしたのにデータが増えない**: `_meta` に前回の記録が残っていて、
  「続きから」の差分取得になっています。`--force-setup` を付けて実行してください。
  詳しくは「[2回目以降は「続きから」取ります](#2回目以降は続きから取ります)」。
- **エラー -303 / -305**: 利用キー未設定／利用規約未同意。`uv run jvstore setup` で設定画面を開いてください。
- **エラー -301**: 認証エラー（利用キー不正、または同一キーを複数マシンで使用）。
- **エラー -116**: dataspec と option の組み合わせが不正。
- **エラー -501**: セットアップのダイアログに答えられていません。`option 3/4` は
  スタートキット(CD/DVD-ROM)の有無を選ぶダイアログを出します。配布は 2022年3月で
  終了しているので「持っていない」を選びます。一度対話的に通せば以降は自動で動きます。
- **32bit / 64bit**: 64bit Python からは 64bit 版 JV-Link が必要です。
- JV-Data は Shift_JIS(cp932) の固定長です。バイト位置で切り出す必要があるため、
  本ツールは受信データを `bytes` のまま扱っています。
